# Documentation review

Content reviewed against the checked-in Artifacts implementation on 2026-09-07. Orbital visual-system update: 2026-09-19.

## Assessment

The previous four-page site described the storage design and a happy-path agent workflow, but did not give an integrator enough information to choose repository boundaries or safely implement updates. The new learning path answers three questions in order: can I make it work locally, how should my data fit, and how do I connect it to my application?

The site now has 22 content pages: 15 in Core (including the introduction), four in Examples, and three in Developer tools. About 80% of the documentation text is in Core. The API reference is a lookup surface alongside the explanatory guides, rather than the starting point for onboarding.

| Developer question | Previous gap | New treatment |
| --- | --- | --- |
| What does Artifacts actually store? | Agent-specific positioning and storage internals came first. | Core concepts defines accounts, namespaces, repositories, files, commits, refs, and forks, with a concrete hierarchy. |
| Can I get a first result without guessing? | Missing clone/setup context, manually assigned remote/token values, and little expected output. | Quickstart captures response values, uses a unique name, shows expected results, proves REST/Git interoperability, and cleans up. |
| How should I model my own product? | A repository per session was presented as the default answer. | Data modeling compares per-run, per-project, per-user, and forked work; ties boundaries to access and retention; shows database mapping and a versioned manifest. |
| What belongs in my database? | Responsibility for business state and discovery was unclear. | Core separates versioned files/history from application permissions, scheduling, schema validation, search, and completion state. |
| How do updates behave? | REST writes could be mistaken for patches. | Snapshot replacement is explicit in the quickstart, data model, writing guide, and API reference, including omitted-file examples. |
| How do I hand off access? | The two token planes and credential response fields were easy to confuse. | Authentication distinguishes account REST tokens from repository Git credentials, explains scope/TTL/revocation, and keeps secrets out of Git arguments. |
| What happens when a request fails? | No retry, conflict, or recovery guidance. | Integration explains transaction gaps, reconciliation, pinned reads, writer ownership, and uncertain outcomes; errors/limits describes current response behavior. |
| Where does the web UI fit? | Local browser behavior was mixed into the core introduction. | Developer tools describes its inspection role, actual tabs, preview limits, and development-only availability. |

## Design decisions

The Orbital visual system takes inspiration from [EVE Online](https://www.eveonline.com/): dark spatial depth, condensed display typography, precise borders, and cyan corner brackets. It retains Artifacts' original stack mark and Tokyo Night accent family, with deeper navy reading surfaces, an uppercase wordmark, numbered navigation, a matching favicon, an editable social card, and a themed 404. The landing illustration turns the Artifacts stack into an original read/work/write-back workflow with real example filenames; it is native SVG, not licensed game artwork or a raster backdrop. The agent runs in the application's runtime, while Artifacts stores its inputs, outputs, and successive snapshots. Barlow Semi Condensed is an open-license, self-hosted display font. Text and code keep their reading-oriented font stacks.

Section navigation still separates Core, Examples, and Developer tools; the sidebar shows the active section's reading path. The three-stage onboarding path and the density of the core documentation are unchanged. Starlight continues to provide production search, code copying, the mobile menu, table of contents, and pagination. The same field-manual framing carries into long reference pages and the four animated explainers, without changing their continuous motion. A light palette preserves the same hierarchy and geometry.

## Motion as explanation

Four authored SVG explainers are placed at the conceptual boundaries where a sequence or changing relationship adds information:

- **Git object graph:** a ref resolves a commit and tree; a changed file adds objects; an unchanged blob is shared; only the ref moves. This supports the integration decision to pin a commit SHA for reproducible output.
- **Snapshot fork:** both repositories initially resolve the same captured commit, then advance independent refs. The graph draws shared history once, avoiding the misleading suggestion that a fork duplicates all object bytes.
- **Publication:** immutable pack and index durability precedes one atomic metadata publication. The animation distinguishes Artifacts’ `pack_wal` from Postgres’ internal WAL and preserves the old reader-visible ref until commit.
- **Storage recovery:** durable metadata and content-addressed pack/index pairs survive a missing local cache. Reconstruction installs a checkpoint, subsequent WAL packs, and current refs. The example explicitly excludes fork lineage rather than silently omitting that rebuild step.

The drawings now use continuous choreography, not chapter-level scene fades: tree connections grow as objects are created, the main ref moves between commits, a fork's copied ref travels into its independent repository, pack/index tiles travel into durable storage, and checkpoint/WAL pairs progressively refill the cache. Native SVG geometry, transforms, and stroke lengths are interpolated from one animation-frame clock with smooth acceleration and deceleration. Persistent objects stay in place across chapters. Arrival timing keeps flight labels separate from the installed state.

Captions and complete transcripts carry the same information as the drawings. Desktop and narrow SVG layouts share the same choreography. Full spatial motion is always enabled. Playback automatically advances and loops, suspends outside the viewport or on document visibility changes, and gives the completed result a short resting interval. Seeking preserves playback; Pause freezes all motion together. JavaScript-disabled pages retain a complete diagram and transcript. The implementation adds no animation dependency or remote asset request.

## Product boundaries documented explicitly

The documentation does not promise path- or branch-scoped credentials, REST patch/merge operations, client-supplied expected-head checks, write idempotency keys, webhooks, cross-account or cross-namespace forks, physical erasure, namespace-region enforcement, or a production web console. These are implementation boundaries, not missing tutorial steps.

Some validation and publication failures currently return generic 500 errors; some empty collections serialize as null; read-only repositories have a WAL-sequence-zero REST bootstrap exception. These details are documented from the code rather than replaced with an idealized API contract.

The onboarding assessment is based on code review, executable examples, and browser inspection. A follow-up usability session with a developer unfamiliar with Artifacts would test comprehension directly; no claim of measured onboarding time or user-study results is made here.
