Artifacts supports independent serving instances backed by one shared Postgres writer and the same S3-compatible bucket and prefix. Postgres is the publication authority, object storage holds immutable Git packs, and each instance has its own reconstructable local cache. Both REST commits and Git pushes use this same storage contract.

| Layer | Holds | Recovery responsibility |
| --- | --- | --- |
| Postgres | Repository ownership, refs, credentials, publication records, checkpoints, and fork lineage. | Durable state; back it up. |
| Object storage (`fs` or `s3`) | Immutable pack and index bytes. | Durable state; preserve every object needed by published refs and descendants. |
| Local cache | Materialized bare Git repositories. | Disposable; the server rebuilds it when missing, stale, or corrupt. |

Your application can rely on a successful publication having durable objects before its refs become visible. It should store commit SHAs for exact versions and read files through REST or Git. WAL sequence numbers and object keys are storage diagnostics, not an application data model.

Instances coordinate publication through Postgres transactions. They do not replicate local caches or require repository ownership, leader election, or object-store compare-and-swap for publication.

## Write path

<Publication />

1. Git receive data is bounded and staged on disk in the repository cache.
2. Git validates and indexes the received objects.
3. New reachable objects are packed into a self-contained incremental `.pack` and `.idx` pair.
4. Both blobs are uploaded under tenant/repository content-addressed keys.
5. One Postgres transaction locks the repository, checks its status/read-only flag and expected WAL sequence, validates every expected old ref, inserts the WAL row and ref-update rows, and publishes all refs.
6. Only after that transaction commits is success returned to Git.

Object durability therefore precedes ref visibility. A failed multi-ref compare rolls back every ref and the WAL record. Uploaded but unpublished blobs are harmless garbage and can be collected later.

## Cache and checkpoints

<Storage />

Bare repositories under `ARTIFACTS_CACHE_DIR/{account}/{repo_id}` are disposable. A keyed process mutex and an OS file lock serialize rebuild, Git RPC, receive, REST commit, and compaction for one repository within a cache directory. Independent instances use separate cache directories. Each cache records the Postgres WAL sequence it represents and is checked with `git fsck`; missing, stale, or corrupt caches are evicted and reconstructed.

Before reconstruction, the server reads repository metadata and refs in one SQL statement, including inside an idempotent commit transaction. This fixes the publication boundary before any object download. A concurrent writer can advance the database while reconstruction continues; the reader still uses the captured refs and only history through the captured sequence. Content range reads and large-object disk fallback use that same snapshot. Checkpoints newer than the captured boundary are ignored; retained immutable history and fork lineage remain usable.

Rebuild order is:

1. parent snapshot lineage, limited to the captured parent sequence;
2. the newest usable checkpoint;
3. later immutable WAL packs;
4. refs and the symbolic default-branch `HEAD` from the same captured database snapshot as the repository sequence.

`artifacts compact --account A --namespace N --repo R` writes the current full pack as a checkpoint. Removing the cache directory does not remove durable repository data. Compaction across instances is coordinated by a per-repository Postgres advisory transaction lock; it does not lock out publications. A checkpoint created from an older snapshot cannot replace a newer checkpoint. Each instance still pays its own cache reconstruction and Git materialization costs.

## Snapshot forks and deletion

A same-tenant snapshot fork records `(child, parent, parent_sequence)` and copies ref metadata in one transaction. It does not copy object bytes. Cache rebuild follows lineage only through the captured sequence, so later parent pushes are invisible to the child.

Deletion moves a repository through `deleting` to `deleted`, which blocks Git and REST lookup immediately and revokes its credentials. Immutable objects and metadata are retained so descendant forks remain reconstructable. Physical garbage collection must account for lineage reachability before deleting packs.

## Legacy data

Migration 001 remains unchanged. Migration 002 adds tenant ownership on repositories, WAL sequence, failure/deletion state, immutable pack/ref-update tables, checkpoints, fork lineage, and job lease fields. The legacy loose-object storer remains readable for migration/import compatibility; all normal publication uses immutable packs.

HTTPS imports apply a hard per-file operating-system quota and stream object counting. The aggregate checkout-size cap is monitored during clone and checked again before publication; it is best-effort between monitor intervals, so deployments should retain an outer filesystem or container quota as defense in depth.

## Integrator implications

A cold file read may take longer while the server reconstructs a cache; clients still receive ordinary file bytes. A transaction protects publication of refs, but it cannot merge two applications' competing snapshots or coordinate your external database transaction. Those belong in your [integration workflow](/artifacts/core/integration/).

Deleting a repository means access revocation and a retained tombstone. It does not promise physical erasure or name reuse. Plan retention with [repository boundaries](/artifacts/core/data-model/) and configure durable storage using the [configuration reference](/artifacts/core/configuration/).
