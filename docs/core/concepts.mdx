Imagine an application that produces research reports. Each report starts with a brief, gains a draft, and goes through revisions. You want to retrieve the version a customer approved, even after someone edits the report again. You may also want a worker to update that report without giving it access to every other customer's work.

Artifacts gives these files a home with history and scoped access. The model starts with a **repository**, a **commit**, and a **branch**.

## A repository keeps related work together

A repository holds files and their history. For our report, it might contain just `brief.md` and `report.md`. Those filenames and formats belong to your application; Artifacts doesn't prescribe a report schema.

Choose a repository around work that shares access and a lifecycle. One report job can have its own repository. A project whose documents evolve together might use a longer-lived repository instead.

This choice also sets the access boundary. A repository credential grants access to the repository and its readable history. Directories and branches do not create separate permissions. If two sets of files need different readers, put them in separate repositories.

## A commit is a version you can come back to

When you publish changes, you create a commit. It captures a complete version of the files and receives a Git commit SHA. Save that SHA when your application needs to refer to an exact result.

A branch such as `main` is a name that moves as new work is published. Use it to find the latest work; use a commit SHA to read a version you already chose.

<ConceptFigure kind="history" />

Suppose a customer approves the first report, at commit B. Your application records B with the approval. A later revision moves `main` to C, but reading `report.md` at B still returns the approved text.

The same principle applies to several files. Publish a report and its supporting data in one commit, then read both at that SHA. Two separate reads of `main` could otherwise see different revisions.

## REST and Git meet in the same repository

Your backend can publish files with an HTTP request. A worker can clone those files, edit them with ordinary tools, and push a Git commit. Your backend can read the result through HTTP without maintaining a clone.

<ConceptFigure kind="interfaces" />

Git is optional for an application that only needs REST. It becomes useful when a worker already uses Git tools, needs to publish binary files, or wants a local workspace. Either way, the files and commits belong to one shared history.

REST updates preserve paths you didn't change. Updating `report.md` leaves `brief.md` in place. Deletion and full replacement are explicit operations. If a change depends on a version you read, send its SHA as `expected_head` so another writer's changes produce a conflict you can resolve. The [writing guide](/artifacts/core/writing-files/) explains version checks and safe retries.

## Your application gives the files their meaning

Artifacts knows that a commit contains files. Your application knows that those files represent an approved report, a completed job, or a project ready for review.

<ConceptFigure kind="ownership" />

Keep the repository address and the relevant commit SHA alongside your business record. Your application still authorizes its users, validates outputs, and decides when work is complete. A new commit is evidence that files were published; it doesn't by itself mean a job succeeded.

When another process needs to work on the files, your backend can issue a short-lived repository credential. That worker can read or update its assigned repository without receiving your account's management token.

## Give each repository an address

A repository address has three parts: **account / namespace / repository**. For example, `acme/research/report-42` identifies a report repository in the `research` group of the `acme` account.

The account owns the repositories and scopes management credentials. A namespace groups repositories within that account; it doesn't restrict an account token's access. Most application code only needs to retain these names, the repository ID, and the commit SHA it plans to read.

You can start with one repository and `main`. When work needs an independent starting point and its own credentials, a [snapshot fork](/artifacts/core/forks-and-imports/) creates a new repository from captured history. You don't need forks to use the basic model.

## Put the model to work

Try the [quickstart](/artifacts/getting-started/) to write and read your first version. Then follow [Integrate into your app](/artifacts/core/integration/) to choose a repository boundary and connect it to your application records.

For deployment and durability details, see [production deployment](/artifacts/core/deployment/) and [storage architecture](/artifacts/storage/). Those explain how the service keeps published history available without making storage internals part of your application model.
